# AI Agent 的高效上下文工程

> 发布日期：2025 年 9 月 29 日  
> 原文链接：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

## 1. 什么是上下文工程

随着大语言模型应用从单轮生成走向能够持续调用工具、执行多步任务的 Agent，工程重点也从“如何写好一段提示词”转向“在每一次模型推理时，应该向模型提供哪些信息”。

**提示词工程（Prompt Engineering）**主要关注指令本身的措辞与组织方式；**上下文工程（Context Engineering）**则关注推理期间进入模型上下文窗口的全部信息，包括：

- 系统提示词与任务指令；
- 可用工具及其说明；
- 外部检索到的数据；
- 对话和工具调用历史；
- 示例、长期记忆与任务状态；
- MCP 等外部信息或工具接口所提供的内容。

因此，上下文工程不是一次性的提示词设计，而是一个持续进行的过程：Agent 每执行一步，系统都需要重新判断哪些信息应当保留、压缩、检索或移除。

文章提出的核心原则是：

> **寻找最小但高信号的 token 集合，使其最大化模型产生目标行为的概率。**

这里的“最小”并不等于越短越好，而是只保留完成任务所必需且有明确作用的信息。

## 2. 高质量上下文的组成

### 2.1 系统提示词：保持清晰，并选择合适的抽象层级

系统提示词需要在两种极端之间取得平衡：

- **过度具体**：把行为写成大量复杂的 if-else 规则，容易变得脆弱且难以维护；
- **过度宽泛**：只给出抽象目标，缺乏足够的行为约束和执行信号。

更合适的方式是给出明确、直接且可执行的指导，同时为模型保留根据具体情况进行判断的空间。提示词可以使用 Markdown 标题或 XML 标签，将背景信息、任务指令、工具规范和输出要求等内容分区组织。

实践中，可以先用能力较强的模型测试一个最小版本的提示词，再根据真实失败案例逐步增加必要的指令和示例，而不是预先堆入所有可能的规则。

### 2.2 工具：少而明确，返回高密度信息

工具是 Agent 与外部环境之间的接口，也会持续向上下文中引入新信息。因此，工具设计不仅影响 Agent 能做什么，也决定其上下文是否高效。

高质量工具通常具有以下特点：

- 功能边界清晰，工具之间尽量减少重叠；
- 输入参数明确、无歧义；
- 返回结果紧凑，只包含决策所需的信息；
- 能够稳健处理错误，并向 Agent 提供可行动的反馈；
- 工具名称和说明能让模型准确判断何时使用。

工具数量过多或职责重叠会制造选择歧义。如果人类工程师都难以明确判断某种情况应调用哪个工具，Agent 通常也很难稳定做出正确选择。

### 2.3 示例：选择少量、多样且典型的示范

Few-shot 示例依然是传达预期行为的有效方式，但不应为了覆盖每个边缘情况而堆积大量案例。更好的做法是提供少量经过筛选的、具有代表性且彼此多样的标准示例，让模型从中归纳行为模式。

与冗长的规则列表相比，一个设计良好的示例往往能更直接地展示输入、决策过程和输出之间的关系。

## 3. 动态检索与 Agentic Search

传统检索系统通常在模型推理前就把可能相关的资料放入上下文。对于 Agent，Anthropic 更强调 **just-in-time context（即时上下文）**：系统先保留文件路径、网页链接、查询语句等轻量级引用，再让 Agent 在真正需要时通过工具加载具体内容。

例如，代码 Agent 无需一开始读取整个代码库，而可以：

1. 先查看目录结构和文件名；
2. 根据任务使用 glob、grep 等工具定位候选文件；
3. 读取相关代码片段；
4. 根据新发现继续缩小搜索范围。

这种方式形成了**渐进式信息披露（progressive disclosure）**。文件名、目录层级、时间戳和文件大小本身就是低成本的元数据，可以先帮助 Agent 判断相关性，再决定是否加载完整内容。

即时检索的优势包括：

- 避免把完整数据集或代码库一次性塞入上下文；
- 减少无关信息对注意力的干扰；
- 让 Agent 根据执行中的新发现调整检索方向；
- 降低预构建索引过期带来的问题。

它也存在代价：运行时探索通常更慢；如果工具或检索启发式设计不佳，Agent 可能反复调用工具、追逐错误线索并浪费上下文。

因此，实际系统往往适合采用**混合策略**：提前加载少量稳定且普遍重要的信息，再允许 Agent 按需自主检索更具体的内容。应选择多大程度的自主检索，取决于任务动态性、延迟要求和模型能力。

## 4. 长时程任务的上下文管理

当任务持续几十分钟甚至数小时、产生的信息超过单个上下文窗口时，仅依赖完整对话历史已经不可行。文章总结了三类主要方法。

### 4.1 上下文压缩（Compaction）

上下文压缩是指在对话接近窗口上限时，对已有轨迹进行高保真总结，并用该总结启动新的上下文窗口。

压缩时应优先保留：

- 已确定的架构或方案决策；
- 用户目标和关键约束；
- 已完成的工作及当前进度；
- 尚未解决的问题与错误；
- 后续步骤所依赖的实现细节。

可以优先删除或压缩：

- 重复的对话内容；
- 已完成且无需再次检查的原始工具输出；
- 不再影响后续决策的探索过程；
- 可以通过引用重新获取的大段数据。

压缩的关键难点是召回率与精确率之间的平衡。初期应优先保证重要信息不丢失，再逐步删除冗余内容。清除较早的原始工具调用结果，是一种相对安全、改动较小的压缩方式。

### 4.2 结构化笔记（Structured Note-taking）

结构化笔记也可视为一种 Agent 记忆机制：Agent 定期把任务状态写入上下文窗口之外的持久化介质，并在后续需要时重新读取。

例如，Agent 可以维护 `NOTES.md`、任务清单或状态文件，记录：

- 当前目标与里程碑；
- 已完成和待完成事项；
- 关键决策及原因；
- 已知错误、依赖和风险；
- 下一步行动。

这种方法以较低的上下文开销维持跨多次工具调用甚至跨会话的连续性。与一次性的压缩摘要相比，结构化笔记更适合具有明确里程碑、需要持续更新状态的迭代开发任务。

### 4.3 多智能体架构（Multi-agent Architectures）

多智能体架构通过任务分工隔离上下文。主 Agent 维护整体目标和高层计划，子 Agent 分别在干净的上下文窗口中执行检索、分析或实现等局部任务，最后只返回经过压缩的结论。

这种方式的价值在于：

- 子任务产生的大量中间过程不会污染主 Agent 的上下文；
- 不同方向可以并行探索；
- 主 Agent 可以集中处理结果综合与最终决策；
- 每个子 Agent 的上下文更聚焦，减少无关信息干扰。

它尤其适合复杂研究和分析任务，但也会引入任务拆分、协调、结果验证和信息合并的额外成本。

## 5. 三种长任务策略如何选择

| 方法 | 更适合的任务 | 核心作用 | 主要风险 |
| --- | --- | --- | --- |
| 上下文压缩 | 需要持续对话和连贯推理的任务 | 将旧轨迹浓缩后延续当前工作 | 压缩过度可能丢失后来才显得重要的细节 |
| 结构化笔记 | 有清晰阶段、状态和里程碑的迭代任务 | 在窗口外持久保存任务状态 | 笔记若不及时更新，可能与真实状态不一致 |
| 多智能体架构 | 可拆分、可并行的复杂研究或分析任务 | 隔离局部上下文，只向主 Agent 返回精炼结论 | 协调成本增加，局部结论可能遗漏跨任务依赖 |

三者并不互斥。复杂系统可以让子 Agent 维护结构化笔记，同时由主 Agent 定期压缩整体轨迹。
